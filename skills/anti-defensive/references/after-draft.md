# 改稿参考

写完初稿后按需要查阅。这里保留旧稿和反馈，帮助判断一句话为什么不合适。例子要连同上下文看。

## 不确定性怎样说

2026-10-02，小Y改写 benchmark 时写了“拦不住就照实说”。Yaobii 的反馈是：“这句话非常的，额，claude，或者llm，不是人说出来的。”

她给的对照是：

> 小王啊，这次活动预算你给我做一下吧，预算上有不确定的可以列出来

“如实告知”“坦白讲”“我无法保证”这类开头，常常可以省去。检查后面的内容：如果某项费用还没报价，就说明哪项待报价；如果一个限制会改变选择，就在作决定前讲清楚。删掉开头以后，这些信息仍要留下。

## 把判断直接说出来

旧稿常先假设读者误解了什么，再用“不是……而是……”纠正。读者没有提出这个误解时，直接写自己的判断和依据。确实需要澄清时，说明具体差别即可。

旧稿也常连续写“A 不等于 B”。把它改成实际要做的检查。

例如，旧稿写过“文件存在≠安装；安装≠调用；调用≠遵循；遵循≠改善了体验”。对应的真实问题是：2026-09-29，一条改法只写进观察记录，Yaobii 追问“你改那个文件没用，应该改几个prompt”。这里需要的动作是修改实际读取的 prompt，核对入口，再从后续对话观察效果。

草稿、模拟数据、尚未验证的功能会影响读者怎样使用结果，标在对应位置。开头已经说明的状态，后面无需反复声明。

## 界面、测试与方案

界面文字要帮助人完成眼前的操作。标签、输入要求、错误原因和恢复办法都可能有用。产品原型中大段解释设计意图的文字，可以移到设计说明里，让人先试用界面。

测试要能发现具体错误。检查主要流程之外，也考虑这次改动涉及的无效输入、权限、数据写入和失败处理。是否需要测试，取决于出错的可能性、后果和已有覆盖；新功能不需要等出过事故才验证。

方案应能说清谁会用、用来做什么。风险判断也要有具体情境：什么操作可能导致什么后果，现有做法能否处理。暂时没有用户抱怨，可以继续查流程或做原型验证；没有依据时先保留为待验证的问题。

## 2026-10-02 的实验记录

旧记录将 benchmark §5.4 原版和改写版分别交给 Sonnet 与 GPT-6.1-sol，让它们写开工前说明和一段方案简介：

- 原版的“停止边界”“无法保证 token 或金额上限”进入了输出。改写初版中的“拦不住就照实说”，在 Sonnet 的三次输出中都出现了。
- 在“记忆系统简介”任务中，附带规则的两组有 9/10 输出加入额度预算；未附带规则的组为 0/5。

这些结果提示要检查 prompt 的措辞和适用范围。每格只有 2–3 个样本；本次修订没有重跑。原文、提示词和输出保存在 `experiment-2026-10-02/`，Sonnet 用 v1，GPT 用删去“拦不住”后的 v2。

旧稿还统计过否定词频率。计数可用来定位重复表达，逐句修改仍要看意思，不设删词数量目标。

## 外部依据（2026-10-02 查过原文的）

- Anthropic Prompting best practices：Tell Claude what to do instead of what not to do；Match your prompt style to the desired output；讲清理由比 NEVER 管用（省略号 / 语音朗读的例子）；新模型对 CRITICAL / MUST 会过度执行。
- OpenAI GPT-5.6 prompt guidance：ALWAYS / NEVER / must 只留给安全规则这类真不变量；精简系统提示在其内部编程评测里分数提高约 10–15%，token 少 41–66%。
- Claude Code issue #93670：规则会让输出偏向，拦不住。
- ai-zixun/humanizer-zh：改中文翻译腔、判断腔，用正面范文和中文作者文风，不用禁词表。
- LessWrong「Demands Are All You Need」：提示越像命令，回答里的对冲越少（小模型，n=900，d=2.67）。
- Artinger & Gigerenzer：防御性决策，明知最好的选项，却选能保护自己的次优选项。
